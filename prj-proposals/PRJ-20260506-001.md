## 2. 核心模块详细分析

### 2.1 大模型管理 (LLM Management)

**架构定位**：Hermes 是一个 Provider-agnostic（ provider 无关）的 Agent 框架，支持 20+ LLM Provider。

**核心文件**：

| 文件 | 职责 |
|------|------|
| `model_tools.py` | 工具发现与函数调用分发 |
| `agent/model_routing.py` | 模型路由（Smart Model Routing） |
| `agent/credential_pooling.py` | 凭证池管理 |
| `hermes_cli/config.py` | Provider 配置定义 |

**设计模式**：

```
Provider 抽象层
├── OpenRouter (API Key)
├── Anthropic (API Key)
├── OpenAI Codex (OAuth)
├── DeepSeek / xAI / Grok
├── Hugging Face / Google Gemini
├── MiniMax / Kimi / DashScope
└── Custom Endpoint (base_url + api_key)
```

**凭证池机制**：

- 支持多个 API Key 轮换（`hermes auth add`）
- 凭证按 Provider 分组，`exhaustion` 状态自动重置
- 支持 OAuth（Nous Portal, OpenAI Codex, Qwen OAuth）

**模型路由**：

```yaml
smart_model_routing:
  enabled: true
  cheap_model: "anthropic/claude-haiku"  # 简单任务自动路由便宜模型
```

**关键设计决策**：

- 所有 Provider 使用统一的 OpenAI-compatible API 格式（`/v1/chat/completions`）
- Provider 之间的差异在 adapter 层抹平
- 辅助任务（vision, compression, session_search）可独立配置 Provider

### 2.2 提示词管理 (Prompt Management)

**核心文件**：

| 文件 | 职责 |
|------|------|
| `agent/prompt_builder.py` | System Prompt 构建（推测） |
| `hermes_state.py` | Session 消息历史管理 |

**设计要点**：

**System Prompt 构建流程**：

```
用户输入
    ↓
加载 Memory (user_profile + 通用记忆)
    ↓
加载 Skills (当前会话预加载的技能)
    ↓
加载工具 Schema (toolsets 启用的工具)
    ↓
构建 System Message (模板 + 动态注入)
    ↓
与用户消息合并 → LLM 调用
```

**消息历史管理**：

- Session 历史以 SQLite 持久化（`hermes_state.py`）
- 支持 `/compress` 手动压缩上下文
- 自动压缩触发条件：`compression.threshold` (default 50% token usage)
- 压缩目标比例：`compression.target_ratio` (default 20%)

**上下文注入机制**：

| 注入内容 | 时机 | 方式 |
|---------|------|------|
| User Profile | 每次 | System Prompt 前缀 |
| Active Skills | 每次 | System Prompt 注入 |
| 工具描述 | 每次 | tools 参数 |
| Session 历史 | 每次 | messages 参数 |
| Memory | 按需 | 检索后注入消息 |

### 2.3 上下文管理 (Context Management)

**核心文件**：

| 文件 | 职责 |
|------|------|
| `hermes_state.py` | SQLite Session Store |
| `agent/context_compression.py` | 上下文压缩（推测） |
| `run_agent.py` | AIAgent 核心对话循环 |

**Session 存储**：

```python
hermes_state.py (推测结构)
├── SQLite: ~/.hermes/sessions/sessions.db
│   ├── messages: session_id, role, content, timestamp
│   ├── metadata: session_id, name, created, updated
│   └── compression_log: session_id, before_tokens, after_tokens
└── Checkpoints: ~/.hermes/checkpoints/ (可选)
```

**上下文压缩算法**（推测）：

- 基于 token 阈值触发（默认 50% context length）
- 压缩策略：保留系统消息、最近 N 轮对话、压缩中间轮次为摘要
- 使用专用 LLM 生成摘要（`compression` model 可配置）

**Checkpoint 机制**：

```yaml
checkpoints:
  enabled: true
  max_snapshots: 50
```

- 文件系统快照，支持 `/rollback` 恢复
- 每个快照是文件系统状态的完整副本

### 2.4 MCP 管理 (MCP Management)

**核心文件**：

| 文件 | 职责 |
|------|------|
| `hermes_cli/commands.py` | MCP 命令注册 |
| `model_tools.py` | MCP 工具发现 |

**MCP 协议集成**：

Hermes 支持以 MCP Server 形式接入外部工具：

```bash
# 添加 MCP Server
hermes mcp addNAME --url <mcp-server-url>
hermes mcp addNAME --command "npx" --args "some-mcp-server"

# 测试连接
hermes mcp test NAME

# 配置工具选择
hermes mcp configure NAME
```

**工具发现流程**：

```
MCP Server 连接
    ↓
通过 MCP 协议发现工具列表
    ↓
过滤已启用 toolsets 对应的工具
    ↓
转换为 Hermes Tool Schema (name, description, parameters)
    ↓
注册到 Tool Registry
    ↓
供 LLM 函数调用
```

**MCP 与 Toolsets 的关系**：

| Toolsets | 来源 | 范围 |
|---------|------|------|
| `terminal`, `file`, `web` 等 | Hermes 内置 | 核心工具 |
| MCP Servers | 用户配置 | 按需扩展 |
| Plugins | 第三方 | 按需安装 |

### 2.5 Skill 管理 (Skill Management)

**核心文件**：

| 文件 | 职责 |
|------|------|
| `agent/skill_dispatch.py` | Skill 调度（推测） |
| `hermes_cli/commands.py` | `/skill` 命令注册 |
| `~/.hermes/skills/` | Skill 文件存储 |

**Skill 本质**：

Skill 是 Markdown 格式的知识文档，包含：

```markdown
---
name: example-skill
description: 做某事的技能
---

# Example Skill

## 触发条件
当用户要求...

## 步骤
1. ...
2. ...
```

**Skill 生命周期**：

```
创建 Skill
    ↓
保存到 ~/.hermes/skills/<skill-name>/SKILL.md
    ↓
注册到 Skill Registry (hermes_cli/commands.py)
    ↓
用户通过 /skill <name> 或 -s <name> 加载
    ↓
Skill 内容注入到 System Prompt
    ↓
LLM 调用时使用 Skill 中的知识
```

**Skill 持久化策略**：

| 类型 | 存储位置 | 持久化方式 |
|------|---------|-----------|
| User Preferences | Memory (memory tool) | 跨会话 |
| 环境配置 | ~/.hermes/config.yaml | 文件持久化 |
| 技能知识 | ~/.hermes/skills/ | Markdown 文件 |
| 会话历史 | SQLite (hermes_state.py) | 数据库 |

**Skill 与 Memory 的区别**：

| | Skill | Memory |
|--|-------|--------|
| 用途 | 技能知识/流程 | 用户事实/偏好 |
| 更新 | 人工编辑或 AI 总结 | 自动写入 |
| 加载 | 显式 `/skill` | 自动注入 |

### 2.6 Subagent 管理 (Subagent/Delegation)

**核心文件**：

| 文件 | 职责 |
|------|------|
| `agent/delegation.py` | 任务委托（推测） |
| `delegate_task()` | 工具接口 |

**两种 Subagent 模式**：

| 模式 | 实现 | 适用场景 |
|------|------|---------|
| `delegate_task()` | 同一进程内子 Agent | 快速并行任务（50次迭代上限） |
| `hermes` 进程 | 独立进程 PTY | 长时自主任务 |

**delegate_task 机制**：

```
主 Agent 调用 delegate_task(goal, context)
    ↓
启动独立子 Agent（独立 conversation）
    ↓
子 Agent 独立运行（max_iterations=50）
    ↓
返回结果摘要给主 Agent
    ↓
主 Agent 聚合结果继续执行
```

**配置参数**：

```yaml
delegation:
  model: "anthropic/claude-sonnet-4"
  provider: "openrouter"
  max_iterations: 50
  reasoning_effort: "medium"
```

**与 Spawn hermes 进程的区别**：

| | delegate_task | hermes 进程 |
|--|--------------|-------------|
| 进程隔离 | 共享主进程 | 完全独立 |
| 迭代上限 | 50 次 | 无限制 |
| 工具访问 | 主 Agent 工具子集 | 全部 |
| 通信方式 | 函数返回值 | PTY / tmux |
| 适用场景 | 批量并行处理 | 长期自主任务 |

## 3. IM 通道管理 (Gateway/IM Channels)

**核心文件**：

|| 文件 | 职责 |
|------|------|
| `gateway/run.py` | Gateway 主入口 |
| `gateway/platforms/` | 平台适配器（Telegram, Discord, Slack...） |
| `gateway/session.py` | SessionStore — 会话持久化 |

**支持平台**：

```
gateway/platforms/
├── telegram.py          ├── slack.py
├── discord.py           ├── whatsapp.py
├── signal.py            ├── email.py
├── matrix.py            ├── mattermost.py
├── homeassistant.py     ├── dingtalk.py
├── feishu.py            ├── wecom.py
├── bluebubbles.py       ├── weixin.py
├── qqbot.py             └── api_server.py
```

**消息流架构**：

```
[Platform] → [Gateway] → [Message Router] → [AIAgent]
                                    ↓
                              [Tool Dispatch]
                                    ↓
                              [Platform Response]
```

**Session 绑定机制**：

```
用户消息来自 Telegram:chat_id=123
    ↓
查找是否有活跃 Session 绑定到 (telegram, 123)
    ↓
有 → 恢复该 Session 继续对话
无 → 创建新 Session，绑定 (telegram, 123)
```

**Home Channel**：
- 每个用户/群组可设置 Home Channel（`/sethome`）
- Cron 任务和通知默认投递到 Home Channel
- 支持跨平台投递：`origin` / `local` / `telegram` / `feishu` / `weixin`

## 4. Tool 管理 (Tool Management)

**核心文件**：

|| 文件 | 职责 |
|------|------|
| `tools/registry.py` | 中心化工具注册表（Schema + Handler + Dispatch） |
| `toolsets.py` | Toolset 定义、`_HERMES_CORE_TOOLS` 列表 |
| `tools/approval.py` | 危险命令检测 |
| `tools/terminal_tool.py` | 终端编排 |
| `tools/process_registry.py` | 后台进程管理 |

**架构特点**：
- 每个 Tool 文件在 import 时调用 `registry.register()` 注册
- `tools/registry.py` 无依赖，被所有 Tool 文件导入（依赖链底层）
- `_discover_tools()` 动态发现，`handle_function_call()` 分发执行

**Tool Schema 结构**：
```python
{
    "name": "tool_name",
    "description": "what it does",
    "parameters": { "type": "object", "properties": {...} }
}
```

**Approval 机制**（`tools/approval.py`）：
- 检测危险命令（rm, git push --force, etc.）
- 需要用户显式批准（`/approve`）才可执行

## 5. CLI 交互 (CLI)

**核心文件**：

|| 文件 | 职责 |
|------|------|
| `cli.py` | HermesCLI 类 — CLI 编排器 |
| `hermes_cli/commands.py` | Slash 命令定义 + 自动补全 |
| `hermes_cli/callbacks.py` | 终端回调（clarify, sudo, approval） |
| `hermes_cli/skin_engine.py` | CLI 视觉主题定制 |

**技术栈**：
- **Rich**：Banner/Panel 彩色显示
- **prompt_toolkit**：输入框 + 自动补全

**核心机制**：
- `process_command()` 解析命令名 → 调用 `resolve_command()` 从中央注册表查找
- 所有 Slash 命令集中注册在 `COMMAND_REGISTRY`（`CommandDef` 对象列表）
- Skill slash 命令通过 `agent/skill_commands.py` 扫描 `~/.hermes/skills/` 注入

**命令别名系统**：
```python
CommandDef("background", "Description", "Session",
           aliases=("bg", "bkg"), args_hint="[arg]")
```
- CLI、Telegram Bot Menu、Slack `/hermes` 都从同一注册表自动生成

## 17. 关键源码详解

### 模式 1：Registry（注册表模式）

**应用场景**：Tool 管理（`tools/registry.py`）

```python
class ToolRegistry:
    """Singleton registry — 所有工具在 import 时自注册"""
    
    def register(self, name, toolset, schema, handler, check_fn, ...):
        """每个 tools/*.py 在模块级别调用 registry.register()"""
        
    def get_tool(self, name):
        """按名查找工具"""
        
    def list_tools(self, toolsets=None):
        """按 toolset 过滤工具"""
```

**变体**：Skill Registry、Command Registry（`COMMAND_REGISTRY` 列表）

---

### 模式 2：Provider Adapter（提供者适配器）

**应用场景**：LLM Management

```
所有 Provider 统一暴露 OpenAI-compatible API 格式
接口差异在 adapter 层抹平
新 Provider 只需实现 adapter，无需改动核心逻辑
```

**Smart Model Routing** 也是一种 Strategy 模式：
```python
smart_model_routing:
  cheap_model: "anthropic/claude-haiku"  # 简单任务路由便宜模型
  expensive_model: "anthropic/claude-opus-4"  # 复杂任务路由强模型
```

---

### 模式 3：Observer / Pub-Sub（观察者模式）

**应用场景**：Approval 机制（`tools/approval.py`）

```python
# 危险命令触发 → 发布事件 → 用户批准 → 执行
if is_dangerous(command):
    await wait_for_approval(user_id)
    # 用户批准后继续执行
```

Gateway 消息路由也是 Pub-Sub：
```
Platform Event → Gateway → Topic Dispatch → Session Handler
```

---

### 模式 4：Singleton（单例模式）

**应用场景**：
- `ToolRegistry` — 全局唯一注册表
- `SessionStore` — 全局唯一会话存储
- `process_registry.py` — 全局进程管理

---

### 模式 5：Chain of Responsibility（责任链模式）

**应用场景**：Tool Dispatch

```
用户消息
    ↓
AIAgent.loop → handle_function_call(name, args)
    ↓
ToolRegistry.get_tool(name) → ToolEntry.handler(args)
    ↓
Tool 实现处理
```

Approval 检查嵌入责任链：
```
ToolRegistry.get_tool()
    ↓
check_fn() — availability check（工具是否可用）
    ↓
Approval check（危险命令需批准）
    ↓
Handler 执行
```

---

### 模式 6：Decorator（装饰器模式）

**应用场景**：Approval 装饰器

```python
@requires_approval("git push --force")
def git_push(args):
    ...
```

---

### 模式 7：Template Method（模板方法）

**应用场景**：Prompt Builder（`agent/prompt_builder.py`）

```
构建 System Prompt 的步骤是固定的（模板）：
1. 加载 Memory
2. 加载 Skills
3. 加载工具描述
4. 注入用户 Profile
5. 合并为完整 System Message

每一步的具体实现可按 Provider/场景定制
```

---

### 模式 8：Composition（组合模式）

**应用场景**：AIAgent Core

```python
class AIAgent:
    def __init__(self, ...):
        self.prompt_builder = PromptBuilder(...)
        self.context_compressor = ContextCompressor(...)
        self.auxiliary_client = AuxiliaryClient(...)
        self.model_metadata = ModelMetadata(...)
        self.display = Display(...)
```

AIAgent 将多个子系统组合在一起协调工作。

---

### 模式 9：Factory（工厂模式）

**应用场景**：
- `model_metadata.py` — 模型元数据工厂（context length、token 估算）
- `models.py` — Provider 模型列表工厂
- Tool Schema 构建

---

### 模式 10：Pipeline（管道模式）

**应用场景**：Context Compression

```
原始消息历史
    ↓
Token 计数
    ↓
判断是否超过 threshold
    ↓
压缩（摘要中间轮次）
    ↓
目标比例 target_ratio
    ↓
压缩后消息历史
```

## 26. 补充模块详解（v2.1.0 新增/完善）

### 26.1 Skill Curator（技能策展人）

**核心文件**：`agent/curator.py`

**职责**：自动追踪技能使用情况、归档闲置技能

**生命周期状态机**：
```
active → stale → archived
         ↑
      idle > min_idle_hours
```

**策展规则**：
- 按 `curator.interval_hours` 定期扫描
- `stale_after_days` 后标记为 stale
- `archive_after_days` 后归档
- `pinned` 技能豁免所有转换
- **从不删除**，最大动作为 archive

**使用追踪**（`~/.hermes/skills/.usage.json`）：
```json
{
  "skill_name": {
    "use_count": 5,
    "view_count": 12,
    "patch_count": 2,
    "last_activity_at": "2026-05-08T...",
    "state": "active",
    "pinned": false
  }
}
```

**自动备份**：归档前自动创建 `~/.hermes/backups/skills-{timestamp}.tar.gz`

---

### 26.2 内存持久化机制（Memory）

**核心文件**：`agent/memory_manager.py`

**三层记忆架构**：

| 层 | 存储 | 内容 | 持久化 |
|----|------|------|--------|
| User Profile | memory (user) | 用户偏好、称呼、沟通风格 | 跨会话 |
| 通用记忆 | memory (memory) | 环境事实、项目约定、工具坑点 | 跨会话 |
| 会话状态 | session | 临时任务进度、待办项 | 会话内 |

**注入时机**：
- User Profile：每次 System Prompt 前缀
- 通用记忆：session_search 召回后注入

**Memory 写入时机**：
- 用户明确纠正时（"记住这个..."）
- 复杂任务完成时（自动总结到记忆）
- 环境检测到关键事实时

---

### 26.3 Kanban 多Agent工作流

**核心文件**：`agent/kanban.py` + `kanban_worker.py`

**架构**：SQLite + 多Profile协作

**核心表结构**：
```sql
CREATE TABLE tasks (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  status TEXT DEFAULT 'ready',  -- ready|claimed|running|blocked|done
  tenant TEXT,
  created_at TIMESTAMP,
  updated_at TIMESTAMP,
  assigned_profile TEXT,
  metadata TEXT  -- JSON
);

CREATE TABLE task_links (
  id TEXT PRIMARY KEY,
  from_task TEXT,
  to_task TEXT,
  link_type TEXT  -- blocks|relates|precedes
);
```

**Dispatcher 机制**：
- 运行在 Gateway 内（`kanban.dispatch_in_gateway: true`）
- 自动 reclaim 过期 claim（无 heartbeat > 阈值）
- 原子化 claim：防止多 worker 抢同一任务
- 连续失败 > 5 次自动 block

**Worker 工具集**（受 `HERMES_KANBAN_TASK` 环境变量控制）：
- `kanban_show`, `kanban_claim`, `kanban_complete`
- `kanban_block`, `kanban_heartbeat`, `kanban_comment`

---

### 26.4 凭证池与 Auth 机制

**核心文件**：`agent/credential_pooling.py` + `hermes_cli/auth.py`

**凭证池结构**：
```python
{
  "openrouter": [
    {"api_key": "sk-or-...", "exhausted": false, "last_used": "..."},
    {"api_key": "sk-or-...", "exhausted": false, "last_used": "..."}
  ],
  "anthropic": [...]
}
```

**轮换策略**：
- 按顺序遍历可用凭证
- `exhausted=true` 的凭证自动跳过
- 手动重置：`hermes auth reset <provider>`
- 凭证耗尽时返回 429 并自动标记

**OAuth 支持**：
- Nous Portal（`hermes login`）
- OpenAI Codex（Device Code Flow）
- Qwen OAuth

### 26.5 Checkpoint 快照机制

**核心文件**：`agent/checkpoints.py`

**配置**：
```yaml
checkpoints:
  enabled: true
  max_snapshots: 50  # 超出后删除最旧的
```

**快照内容**：
- 整个 `~/.hermes/` 目录的副本
- 包括 config、sessions、memories、skills

**回滚**：`/rollback [N]` — 恢复到 N 个快照之前

**用途**：
- 危险操作前自动创建（`rm -rf` 等）
- 实验性修改前保护

| 适用 | 动态任务 | 静态任务列表 |
| 并行 | asyncio.gather | multiprocessing |

### 33.3 问题诊断

**问题1：单文件过大（3403行）**

- 难以独立测试 SamplingHandler
- MCPServerTask 的 asyncio 逻辑与业务逻辑耦合
- Handler 工厂函数分散在文件各处

**问题2：命名污染**

- 全局变量 `_servers`、`_server_error_counts`、`_server_breaker_opened_at`
- `_lock`（全局锁）与其他模块的锁命名冲突风险
- 模块级状态让并发测试困难

**问题3：错误处理分散**

- `_handle_auth_error_and_retry`（1724行）与 `_handle_session_expired_and_retry`（1880行）功能重叠
- Circuit breaker 逻辑分散在多处（handler、server task、模块级 dict）

### 33.4 推荐拆分方案

```
tools/mcp/
├── __init__.py          # 导出 register_mcp_servers, discover_mcp_tools, get_mcp_status
├── constants.py         # _DEFAULT_TIMEOUT, _CIRCUIT_BREAKER_* 等常量
├── sampling.py          # SamplingHandler 类（566-936行）
├── server.py            # MCPServerTask 类（937-1630行）
├── handlers.py          # _make_*_handler 工厂函数（2157-2567行）
├── schema.py            # _normalize_mcp_input_schema, _convert_mcp_schema, sanitize_mcp_name_component
├── registration.py      # _register_server_tools, register_mcp_servers, discover_mcp_tools
├── lifecycle.py         # shutdown_mcp_servers, _kill_orphaned_mcp_children, _stop_mcp_loop
├── transport/
│   ├── __init__.py
│   ├── stdio.py        # _run_stdio 逻辑
│   ├── http.py         # _run_http 逻辑
│   └── sse.py          # _run_sse 逻辑
```
